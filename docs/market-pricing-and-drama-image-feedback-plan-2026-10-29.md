## 2. 定价保存：为何会同时报成功与失败

源码链路（路径相对 web/server 各仓库）：

1. `web/tenant/src/views/power_mall/market.vue:832` 的 `savePricing` 按 `product_id` 分组后 `Promise.all` 并发调用保存。一个应用包含多个 API 商品，对应多个独立数据库事务。
2. 同文件 `815` 的 `toggleAppShelf` 也并发保存应用内商品。`savePricing` 没有函数入口重入保护；首个请求 reject 后，`finally` 会清除 loading，其他请求仍可继续提交。
3. `server/app/tenantapi/controller/power/MarketController.php:70` 每个成功请求返回 `show=1`；`web/tenant/src/utils/request/index.ts:61` 逐请求弹提示；页面 `851` 又单独提示成功。部分请求提交而另一些失败时，红绿提示并存有明确源码解释。
4. `web/tenant/src/utils/request/axios.ts:105` 明确禁止 POST 自动重试，**不能把本次死锁归咎于全局自动重试**。
5. `server/app/common/service/power/TenantPowerMarketService.php:257` 事务外读取平台商品/SKU，事务内按请求原顺序写入；每个改价 SKU 调用 `MarketPriceRuleService::manual`。
6. `MarketPriceRuleService.php:118` 每次人工改价均先对 owner `0`、再当前租户执行 `INSERT IGNORE` 与 `FOR UPDATE`，随后修改规则并增加 revision。不同商品、甚至不同租户也可能竞争平台 owner `0` 热点；SKU 未按稳定 ID 排序。
7. 平台 `PowerMarketService.php:81` 能力校正保存存在商品→owner 锁序，规则 `MarketPriceRuleService.php:235` 存在 owner→SKU/商品锁序。跨入口反序是明确风险；本次是否触发该路径仍需等待图。

因此，顺序保存能减轻同页竞争和提示混乱，但**单改前端串行不足以解决所有数据库竞争**。不能把弹窗合并视为死锁已经修复，也不能在部分提交后提示“全部保存成功”。

### 2.1 最小兼容实施步骤

1. 保留现有页面、保存按钮和逐商品接口；冻结本次提交的商品/SKU/编辑值快照，按稳定商品顺序保存；添加函数入口防重入。加载状态覆盖全部请求及结果核对，保存时避免刷新、恢复、溢价、上下架造成同一数据重叠写入。
2. 对该组合操作启用请求级静默提示，由页面只报告一次最终结果。全部提交才报整体成功；部分成功明确数量和失败 API，保留未保存输入；“保存成功、刷新失败”与“保存失败”分开。其他页面的默认提示行为不变。
3. 后端统一租户改价、平台能力保存、价格规则应用与目录同步涉及共同表时的锁序。实施时列出所有共享写入入口，确定并记录统一 owner/商品/SKU 顺序；一次事务只获取一次必要 owner 锁，SKU 按稳定 ID 写入，不能留下一处反序入口。
4. 平台 owner `0` 热点是否可缩减，先核对规则继承和 revision 一致性要求；不能为提速绕过平台规则校验。对 `INSERT IGNORE → FOR UPDATE` 的具体竞争，取得等待图再决定调整，不能凭猜测删除锁。
5. 每次本地事务尝试重新读取并校验平台状态、SKU、成本和租户配置，保证失败时该商品价格、状态、规则和 revision 一起回滚。不能用事务外旧数据通过校验后直接提交。
6. 死锁恢复只覆盖**已确认完整回滚的本地配置事务**，识别真实 SQLSTATE/驱动错误后短退避重读重做。1213、1205、连接断开与提交确认丢失分别处理；业务校验、权限失败与用户取消不盲重试。单次请求仍受真实连接/运行时约束；未成功必须如实返回可恢复失败，不能吞错报成功。这不是创作预算或生成次数封顶。
7. 上下架仅表达状态变更，后端读取当前价格，避免 `saveProductShelf:763` 把旧页面价格写回，也避免未改价就默认建立人工价格规则；用户确实改价时仍保持现有规则语义。
8. 用原值或配置版本检测并发编辑，不能“最后写入的旧页面”静默覆盖新售价；重复相同值不重复建行、不无意义增加 revision。现有唯一索引只能防重复行，不能解决旧值覆盖。
9. 维持现有逐商品事务边界，不宣称整个应用原子保存。超时/取消不等于回滚；结果不明先回查，核对成功项后只恢复未成功项。刷新返回的旧响应不能覆盖较新的本地编辑。

迁移文件已声明 `(tenant_id, sku_id)` 与 `(owner_id, scope_type, scope_id)` 唯一索引（`20260718_power_market.sql:26`、`20261022_market_price_rules.sql:12`）；运行数据库是否执行过尚未核查。后续先只读核验实际表结构、版本及死锁信息，再决定是否需要迁移，本方案不执行 SQL。

目录同步也必须兼容：现有同步会拉取上游目录/报价；本地配置事务重放不得再次发起这些外部请求。保留租户自定义售价、人工规则和停用策略；不借修死锁重置价格或重上架。

## 3. 短剧生图：正文可见为何仍提示缺 prompt

### 3.1 已确认的具体调用顺序

1. `web/pc/pages/ai/short-drama/plan.vue:4193` 的 `createVisualTask` 发送 `visual_prompt/image_prompt/subject_prompt/scene_prompt`，没有根级或嵌套的 `prompt`；取值为 `visual_prompt || unified_prompt || description`。这是接口契约不一致，**本身不足以证明本次错误根因**。
2. `web/pc/components/short-drama/VisualCreationWorkbench.vue:3540` 场景、`3606` 主体创建均先 trim/非空校验，兼容 `image_prompt`，同时发送根级/嵌套 `prompt`、可见及内部提示词。工作台已使用 `web/pc/utils/short-drama-batch-submit.ts` 逐项提交与回查，策划页却另用 `Promise.all`。
3. `GenerationController::create` 将请求交给 `AigcShortDramaService::createShotGenerationTask`。服务完成模型/比例等处理后，调用 `estimateImageGenerationBilling`（`15434`）。
4. **报价已经组装最终提示词**：先取得模型快照，再调用 `shortDramaImageParams`（`11977`），使用现有模板、主体/场景资料和画风，再将 `$params` 与 `$imageParams` 合并传给市场 `quote`。不能描述为“本地后端在组装提示词前就要求 prompt，已证实”。
5. 报价通过后创建短剧任务；执行时再次组装 imageParams、编译引用，`runMarketImageGenerationTask:8000` 将模型选择和最终 imageParams 分别传给市场 `reserve`，随后 `submit`。市场预占与提交均有 `prepareRequest` 校验；三处最终业务参数必须一致。
6. `MarketGenerationSchema.php:148` 在必填值不存在、null、空串或空数组时抛出截图同文案。`MarketGenerationRequest` 根据 native mode、Schema、defaults、provider_params、locked_params 编译请求；旧协议另走 `normalizeLegacyPayload`。

当前源码证据意味着：要找到“原输入已有内容”到“校验视角缺字段”的确切位置，而不是要求用户重写整个剧本或换模型。

### 3.2 待验证分支与对应处理

| 要核对的分支 | 可能出现的情况 | 优化要求 |
| --- | --- | --- |
| 策划页字段/类型与工作台不同 | 已有 image_prompt 未选用；空白字符串阻断后续 fallback；旧对象缺字段或类型异常 | 对齐既有安全字符串取值及别名，明确人物/场景 ID；不能把数组硬转字符串或用占位 prompt 掩盖缺失 |
| 最终提示词为空或模板来源错误 | 页面正文存在，不等于该主体/场景的有效提示词已传递 | 保留现有模板与资料优先级；检查当前版本的权威人物/场景和用户明确修改，只恢复缺失引用，不重写合格剧本 |
| 最终 prompt 非空，nativeInput 却缺失 | 协议转换/白名单过滤丢字段，或结构化 `input.messages` 请求与平面 `prompt` Schema 不匹配 | 以真实渠道协议和已声明契约对齐编译及校验视角；结构化正文不能被误判为平面字段缺失，也不能给真实必填字段放水 |
| defaults/locked/provider 参数与业务提示词冲突 | 空值或过期目录契约覆盖了最终值；可能同名字段语义不同 | 核对实际模型元数据及字段所有权，不盲目合并；保留业务负责的提示词、SKU 负责的合法规格及服务端保护字段 |
| 报价、预占、提交三次准备不一致 | 报价能过，创建后失败；提示词、引用或规格在重组时变化 | 一次规范化、确定性复用同版本内容和模型身份；现有请求签名/计费所需参数贯通，提交前检查一致性 |
| 客户版本或元数据与本地不同 | 客户仍运行旧路径，或目录刷新改变协议 | 对照部署 SHA、worker 版本、任务和模型快照；兼容历史任务，不对已受理任务套用新模型/价格 |

这些分支是排查树，不是已证实的客户唯一原因。特别是 Qwen Image 2.1，不能套用仅针对 Qwen Image 3.0 的专属参数规则，也不能为绕过校验静默替换到另一官方/三方模型。

### 3.3 不改变用户创作方法的修正步骤

1. 保留“剧本策划 → 现有生成主体场景图按钮 → 原创作工作台”的步骤、收费确认及手动/自动方式，不要求用户新增 prompt 表单或重新走一遍策划。
2. 建立策划页与工作台共享的输入契约，明确用户输入、人物/场景文本、旧别名、可见/内部提示词、引用资料的来源与优先级。缺字段先按既有权威资料补齐；冲突保持原明确用户修改优先，不拼接无意义占位词。
3. 继续使用现有服务端提示词构建函数与模板，不新增一次 AI “补 prompt”收费调用。报价、预占和实际提交使用同一版本、同一模型/SKU/规格及等价最终内容；禁止只在前端补一项便宣布链路修复。
4. 先做本地合法性检查及真实协议完整校验，再预占/提交。真正前置规划估价尚未有 prompt 时，只能使用现有 `quoteForFuturePrompt` 的受限语义；实际生成与受理校验绝不跳过必填。此反馈路径后端已组装 prompt，应修正丢失/协议错配，而非改为跳过。
5. 对齐现有 `submitShortDramaBatch` 的逐项提交、节奏和回查方式，不另建创作流程。冻结本次目标集合，按项目/剧集/实体/内容版本区分；保留已完成和已受理项，只恢复缺项；不能在首项失败后让其余请求脱离管理。
6. 明确“已受理、明确未受理、受理不明、已完成、旧失败”分别如何处理。当前策划页把所有历史任务 key 都计入 existing，旧失败项存在无法重新提交的风险，应核对并复用既有失败恢复方式；不能把失败记录永久当成已完成，也不能自动重放受理不明的收费 POST。既有批次助手通过 string/Error 区分业务拒绝与传输未知，这不能作为长期受理依据；复用时保留回查并补齐明确错误码/受理事实，尤其不能因启用静默提示改变异常类型就改变恢复判断。
7. 模型设置保存失败不能无条件吞掉后继续收费：区分仅偏好保存失败与影响本次请求的权威设置/版本冲突。前者如原协议允许，使用明确冻结的当前请求继续并提示偏好未保存；后者在原按钮处准确报告并恢复，不能退回默认模型悄悄生成。
8. 一次用户操作统一展示角色/场景已受理、明确失败、待核对数量及具体对象，不连续刷同一报错。沿现有页面/工作台展示和恢复已受理结果；不能用“已提交”代替“全部生成成功”。
9. 原有模型真实能力、素材归属及计费校验保留。公共图片运行时当前还有 `SUBMIT_MAX_ATTEMPTS=3` 与 `SUBMIT_LANE_WAIT_SECONDS=30`，纳入封顶排查：单次工作片可结束，**不能因累计次数/等待片到限把可恢复创作记为终态失败**。仅对明确未受理的临时拒绝延迟续处理；受理不明先查原任务，不以取消次数封顶为由重复请求。

### 3.4 必须补齐的定位信息

在现有任务/诊断体系记录并关联以下内容，前台仍只显示简明错误与原详情入口，不把内部诊断塞进创作表单：

- 项目/剧集/人物或场景 ID、业务任务 ID、请求关联号、部署版本；有消费或上游 ID 时关联原记录。
- 阶段：输入规范化、提示词构建、协议编译、报价、预占、上游提交、结果转存。
- 最终 prompt 是否存在、类型、字符数与摘要 hash；模型/SKU/官方或三方来源、native mode、Schema/模板版本、参数签名。
- 校验缺陷字段路径与错误码、实际 outbound 字段路径清单；原始内容仅在有权限的诊断记录中按原规则保存，不能泄露密钥/签名地址。
- 费用与受理事实：校验前拒绝、是否预占、是否实际提交、是否有上游回执、是否待核对；不能根据一句前端 toast 推断已经扣款或没有扣款。

## 4. 费用与结果准确性

截图的“80 积分”只是按钮展示，不能证明发生了 80 积分扣款。核对原定价、实际目标数量、每项规格、预占和消费流水后才能说明实际费用。未提交的本地格式适配、字段继承、配置保存和回查不产生模型费用；实际新增模型调用仍由用户按原价格承担。

前置校验失败不得新增模型请求或消费预占；若历史失败已经存在预占，先核对原任务、消费编号与上游受理，沿原资金服务处理，不手工改成 refunded。已受理/已产生真实用量，不能因后续本地异常就声称未收费或全额退回；结果未知应保留待核对。

API 配置事务恢复只修改配置，不调用外部模型、不触发用户/租户资金流水，也不改历史价格快照。新售价影响后续业务按原价格生效规则执行；旧任务不因配置修复重新定价。

## 5. 实施与验收顺序

1. 固定当前成功样本、原操作方式和价格语义；收集脱敏的错误请求、Schema、最终请求与数据库等待图。客户现场资料暂缺时可先用本地已证实缺口做回归用例，不把本地构造样本宣称为客户复现。

3. 修策划页到市场图片运行时的参数契约、协议视角、模型/内容版本一致性，复用现有工作台批次恢复方法；不改变主体/场景生成方法。
4. 与剧本 Schema/角色场景补缺、多集完整性、取消累计停止线、画布与费用方案共同执行兼容回归。
