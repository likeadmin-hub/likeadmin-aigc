# 小程序虚拟支付与套餐优惠运维

本功能默认关闭。部署和发布状态以对应版本的验收记录为准。

## 配置顺序

1. 部署时执行五份 20261014 静态迁移：package_promotion、virtual_payment、virtual_payment_orders、virtual_payment_platforms、virtual_payment_recovery；新装与新租户菜单已同步。按升级器正常执行，不手工重复建表。
2. 在租户虚拟支付页面点击“生成密钥”，系统为当前租户独立生成并保存支付凭据加密密钥；首次保存支付配置时也会自动生成。无需修改服务器配置、填写加密密钥或执行命令。已生成的密钥不会因再次点击、重复保存、切换环境而更换；微信 AppKey 仍需从对应小程序微信后台取得并填写。
3. 租户进入“财务管理 → 套餐管理 → 虚拟支付”。AppID 自动从渠道配置或有效小程序授权读取，无需填写；再配置 OfferID、环境、AppKey，并分别勾选 iOS、Android。允许单选、多选、全部取消；全部取消即关闭。AppKey 不回显，留空保持不变。旧交易保留原配置版本。
4. 手工接入小程序：复制本租户页面生成的消息推送地址，按实际 Token、EncodingAESKey 和加密方式配置微信后台。开放平台授权模式继续使用原授权消息接收地址，不向租户下发平台共享推送密钥。
5. 在算力/会员套餐“优惠与道具”中配置普通价、优惠规则、优惠价格与时长；为每个购买周期分别绑定常规、优惠道具及对应价格。道具需在微信后台发布。系统按 AppID、环境、套餐、周期与价格严格匹配，不用全局兜底道具绕过校验。
6. 开启虚拟支付前完成微信平台资格、iOS 条件与真机验证。页面保存成功仅表示本地配置有效，不证明微信已批准收款。

## 优惠与支付行为

- 新人时限从注册时间计算，全体活动从首次启用计算；满足任一规则即可。普通保存不重启倒计时，显式重启也不恢复已使用次数。
- 每个用户在同一租户的同类套餐只享受一次成功优惠，会员不同购买周期、PC/H5/小程序共用次数。退款不恢复次数。
- 服务端生成报价、30 分钟锁价订单及权益快照。等待渠道结果的订单必须先核对或关闭，不能通过重新下单释放占用。
- 小程序仅在勾选的终端使用原生虚拟支付；未勾选终端沿用原渠道支付配置，PC/H5 保持原流程。客户端返回成功不作为到账证据。
- 已启用的旧配置升级后默认保留 iOS、Android，关闭的旧配置保持关闭。旧小程序未传终端时保留虚拟支付限制，独立终端选择需使用同步更新的小程序包。新表字段由全新安装 SQL 和独立升级迁移共同覆盖，新租户按相同共享配置表默认关闭。
- 公共购买接口固定现网。沙箱配置仅供隔离诊断，不允许客户传参切换到沙箱领取生产权益。
- Android/iOS 的能力判断与错误提示已实现；iOS 还受微信版本、系统、Apple 账号地区及最低金额等渠道条件约束，真实资格以微信最新说明及真机结果为准。

## 核对、发货与退款

统一入口 `scripts/start-ai-task-worker.sh` 已内置虚拟支付核对循环：启动后执行一次 `virtualpay:maintain`，本轮结束后等待 60 秒再执行，不启动整套 cron，也不并发叠加同一循环。核对失败只重试支付核对；支付循环退出时只恢复该循环，不重启现有 AI/OEM 队列。

迁移中的每分钟 cron 项保留兼容独立调度部署。两入口共用同一数据库进程锁，已有核对正在执行时直接跳过；交易、权益和任务仍使用已有幂等及租约保护。无需新增宝塔守护配置。

停止统一脚本时，支付循环不再派发下一轮；当前有界核对忽略 TERM/INT 并完成持久化后退出，其他队列沿用原有退出流程。Supervisor 的强制 KILL/机器断电无法保证等待完成，未结束订单由原查单与租约机制恢复；不要缩短现有退出等待时间。人工诊断仍可运行 `php think virtualpay:maintain`。本次只改本地代码，没有重启任何现行业务进程；部署后在正常排空更新窗口重新启动原统一入口才会加载新增循环。

后台订单列表分别显示付款、权益、渠道发货与退款结果。异常时点击“重新核对”；此操作按原订单查渠道，不直接标记支付成功。内部异常保留诊断记录，页面使用中文建议。

- 已付款但权益失败：原订单重试，不能重新收费；优惠次数已消费。
- XPay 发货确认与普通订单发货管理分开处理。通用发货未知结果先查单，不盲目重复上传。Apple 订单没有微信交易号时，不伪造物流单或交易号。
- Android 主动退款先检查权益归属和消费记录，再按固定退款单号查单/申请；受理不等于退款成功。
- Apple 退款由用户/渠道流程发起，后台不提供开发者直接退款承诺。
- 已消费、冻结、叠加会员、正在运行任务或归属不明的权益转人工处理。退款到账与权益回收分别记录，不取消 AI 任务、不改动无关权益。
- 原支付配置改变、结果不明、部分退款或重复到账，保留原资金记录和待处理状态，由管理员核对，不能直接删除订单。

关闭新支付入口不等于清除旧交易；须继续运行核对任务，保留原凭据版本和加密密钥。测试网关仅存在于 `tests/Support/VirtualPayAcceptance`，依赖明确隔离数据库与环境限制，不能作为生产路由部署。

## 租户凭据密钥生成与兼容

租户进入“财务管理 → 套餐管理 → 虚拟支付”，在“支付凭据加密”项点击“生成密钥”。页面只显示“未生成/已生成”，不会显示或下发原始加密密钥。生成只更新该租户密钥状态，不覆盖已编辑但尚未保存的 AppKey、OfferID、Token 或 EncodingAESKey；首次保存也自动生成，所以新租户不必先完成独立的运维配置。

生成操作复用虚拟支付保存权限与认证租户身份；客户端传入的 tenant_id 不能选择其他租户。服务器将随机租户密钥按现有渠道凭据机制加密后存入租户配置，密钥封装携带租户身份；新的支付凭据和小程序登录会话使用带租户校验的新密文格式。重复生成、并发生成、重复保存均保留已有密钥；损坏的现有密钥不能通过再次生成覆盖。交易金额、支付签名、查单、发货及退款逻辑没有改变。

旧版已成功保存的支付配置和会话继续按原安装密钥解密。生成租户密钥不会改写历史版本；重新保存配置时，新版本使用租户密钥重新封装留空保持的凭据，旧版本仍供历史订单使用。因此原安装备份仍需保留，不能主动删除或更换历史密钥。对于从未成功配置过的新租户，不需要 `virtualpay.credential_key`、`.env` 或 `virtualpay:key` 初始化命令。

后台、回调和支付维护任务均使用配置版本/会话行的明确租户ID解析凭据，不依赖当前请求的租户上下文。备份应包含租户配置、支付配置版本及原有渠道凭据保护信息；若历史密钥丢失，应恢复原备份，不能用新生成的租户密钥冒充原密钥。

本次撤掉了此前新加的站点 `.env` 自动生成和 `virtualpay:key` 命令。支付配置保存成功仍只表示配置已持久化，不代表微信真机支付、回调与发货已验收。
