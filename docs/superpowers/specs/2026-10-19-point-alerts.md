# Point balance alert design

Approved in chat: platform alerts tenants; each tenant alerts only its own users. Reuse message-management navigation, SMS engines and existing account balance sources. Add one point-alert menu beneath message management, with rules/records tabs. Tenant power mall embeds platform-alert recipients and inbox. User notices remain private, including PC/mobile reads.

Rules: at most 10 distinct nonnegative decimal thresholds, inclusive comparison, at most two decimal places; per-cycle max 3, per-Shanghai-day max 3, minimum interval 60 minutes (all configurable). Repeats default off, optional repeat interval >= minimum interval. Each admitted round consumes one counter even with multiple recipients/channels. One drop across many levels sends the most urgent level and covers less urgent levels. No channel bypasses the hard caps. Daily counters persist through cycle recovery. Reset cycle only after balance is above highest threshold plus 5% (minimum 0.01 points) for 10 minutes. Small topups/refunds do not reset. Current balance is already net of reservations. Pending rounds revalidate current rule/balance before sending; recovered/disabled accounts cancel pending delivery. Sending/unknown external results are never automatically retried.

Durability: balance-log hooks mark a dirty account in the balance transaction, no outbound I/O. Missing alert schema must not break billing; scheduled keyset scans provide fallback. Account lock serializes counters and admission; deliveries have durable unique keys and leases. Explicit tenant table resolution supports split tables. Sending uses notification-owner settings, never implicit request source. Defaults disabled; no automatic historical mass send. Manual scan previews counts and confirms queued checks; no counter bypass.

Contacts: tenant-specific recipient settings; users use bound mobile by default and may opt out of SMS. Private in-app messages and sender-branded text; no tenant cost exposed to users. The approved phased rollout ships existing SMS plus private in-app delivery first. Email/SMTP and email binding are phase two; phase one explicitly rejects enabling email and shows unavailable status. Tests never send real outbound messages.

No production deployment, package publishing, remote push or historical rebilling. Fresh install, upgrade mirror, tenant bootstrap menu and split-table runtime menu sync must agree.
