# 两项客户升级故障核查与依赖修复

日期：2026-11-11。核查基线：服务端 develop `c7a3780096`，系统 1.0.439。

## 1.0.430 快照容量迁移中断

- 本地历史归档 1.0.430 包含抛出“生成快照容量迁移缺少原字段”的旧实现。
- `7e33bd8b36` 已增加真正缺失字段的修复：仅对受审查的快照列增加 nullable MEDIUMTEXT，并重新读取确认；该实现首次随本地 1.0.435 系统归档交付。不是本次新修复。
- 在本机 PHP 8.2.34 / MySQL 5.7.44 上，现有回归的已有字段扩容、两种反斜杠模式、LONGTEXT 不缩容、13 个缺失字段补齐、重复执行及原始数据保留全部通过。不能据此证明客户现场查询正确，也不能把“MySQL 5.7 大小写/驱动问题”当成已证实根因。
- 客户建议构造 `['data_type'=>'text']` 不可采用：缺少字段名、默认值、NULL、字符集、排序规则和注释，无法保留原字段语义；`columnSql()` 的空返回仅表示已核验字段容量充分，并不负责兼容未知结构。
- 截图明确已处于 SQL 结果未知保护状态。修复代码不会自动解锁旧回执，也不能证明前面其他 SQL 是否执行。必须核对站点实际连接库、表前缀、目标字段完整定义、首个错误及更新回执，才能制定该站点的恢复步骤。不要删除回执、伪造 SQL 完成或反复自动重放。

## 1.0.434 智能文案缺失

- 本地 1.0.434 和 1.0.439 ZIP 均没有 `files/app/apps/aigc_copywriting/`，也没有该应用服务目录。1.0.430 有部分文案文件，不代表后续包能修复缺目录站点。
- `SystemPackageUpdateService::finalizeRuntimeApps()` 无条件调用 `CopywritingBootstrap::ensureSystem()`；该方法读取文案 manifest 和 API schema，后续租户初始化还读取种子数据与文档契约。
- 原 staging 仅根据相邻 Git 差异补齐变化应用的元数据；官方打包器固定补齐的六个应用也没有文案。应用未变化时会再次漏包。

本次修复继续使用现有 staging、打包器、清单和签名格式。普通系统 staging 检测到文案完成钩子时，无论应用相对基线是否变化，都复制完整应用目录、服务、模型、三端控制器及专属 worker/repair 命令；包括历史数据模板和契约。缺少依赖直接阻止构建。新增文件按目录递归自动携带。

验包器从 1.0.430 起要求这些依赖存在，即使本包没有变化的更新器文件；也根据包内调用者识别依赖，防止只放空 manifest 通过。文案历史 SQL 保持原字节，由既有应用迁移日志执行，不作为未变化的系统 SQL 重放。不会跳过初始化或伪造应用注册。

这是现有系统包依赖完整性的修复，不改变包布局、版本链、签名格式或 SQL 排序。旧版 390→391 桥接外壳仍遵守原有独占载荷规则。新安装完整包的默认应用范围不在本次改动中。
