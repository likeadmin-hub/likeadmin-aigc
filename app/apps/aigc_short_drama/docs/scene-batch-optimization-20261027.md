# 相邻小场景生成优化

## 范围

源版本 1.0.41，在原上下文去重基础上，允许同一集内两个相邻的完整小场景共享一次文本生成请求。每场最多两个镜头，合计不超过四镜，并受当前模型输出容量限制。保持原场次顺序、镜头编号、地点、时长、关键事件、进出状态和对白要求。

新请求由服务端写入输入契约 14 与冻结的 `_scene_batch_policy`；客户端不能扩展合并范围。旧契约、启用前已创建的关闭策略任务、自定义模板、时间码任务、复杂转场/回忆/长对白/跨地点移动及地点不一致的骨架继续沿用逐场流程。场景规划不改变用户选定的模型、单价、输出上限、计费权威或旧作品。

只调整 server 的生成与恢复服务，无 web、公开 API、权限、菜单或数据库迁移变更。前端无需新增操作。

## 验收、修复与恢复

- 原始创作资料和全剧连续性仍完整传入。每场的 scene_beat、required_shots、scene_progress 直接保留，后场承接前场，但不能提前演出后场或后集事件。
- 模型返回后逐场校验 ID、顺序、数量、角色、场景语义和时长。验收范围只限所属场景，其他历史场次的错误不会让合格结果被一并丢弃。未知、重复、乱序的镜头使该批次归属不可确认，转入原有局部生成路径。
- 合格场景直接复用；不合格场景单独生成，携带已收到的内容及相邻合格结果，要求保留已有合格动作、对白、说话主体和事件顺序。原有整集质量/连续性复核的启停策略保持不变。
- 只有已经收到、持久保存的模型回包发生结构或内容校验失败时才允许局部回退。提交、未知结果、结算、取消、余额和预检异常不自动触发额外请求。
- 通过原规划单元表保存一个 `checkpoint_scene_batch_v1`，状态为 checkpoint、attempt=0，不是付费回包。它在首次合并请求前固定骨架签名、分组和分段容量，持有数据库锁期间不调用模型。
- 恢复时复用原检查点和付费回包。若旧 worker 已经按逐场方式开始了同一任务，整个任务保持原路径；上下文变更或检查点损坏则明确停止，不绕过旧回包另发付费请求。继续/重试不会重置该检查点。
- 合并单元使用独立 `timed_batch_*` 名称，经原 PlanningUnit 和统一文本模型服务执行；所有实际消耗仍由原统一服务结算。未新增钱包或第二次扣费路径。

## 离线与真实验收

2026-10-27，原十集样本的 35 次分场请求，最终保守规则可规划成 28 次：仅有七对符合规则。此前只按镜头数量得到的 24 次，以及初版保守规则的 26 次，都不作为最终效果承诺。实际次数取决于新骨架和失败修复。

经用户分别批准，执行两次真实 kimi-k3 请求。每次禁用模型切换、兼容重试和瞬时重试，沿用原输入/输出单价 10000 点/百万 token；未重新执行历史逐场基线，也未改动原项目或账单。

| 验收 | 结果 | 实扣点数 |
| --- | --- | ---: |
| 第一次合并对照 | 一个场景因历史骨架将老屋与资料室绑定混用而被正确拒绝，保持默认关闭 | 87.40 |
| 第二次合并对照 | 两个预检合格场景均通过 ID、顺序、地点和时长校验；对白逐字保留，夜间观察与白天查档顺序、未知汇款人悬念保持 | 90.29 |
| 两次额外验收合计 | 各一次提交、一次结算、一次用户扣点，未自动重试 | 177.69 |

第二个样本的两场历史逐场账单为 201.83 点，本次合并为 90.29 点，减少 111.54 点，约 55.3%。新请求用量为输入 8586、输出 443、合计 9029 token。该样本同时包含上一轮上下文去重和本轮合并效果，不代表整部十集或其他模型的固定降幅；验收费用是额外测试消耗，不是退还历史费用。消费记录 5427、5428 可供本机账本追溯。

第一次验收暴露后，补充了跨地点移动/地点不一致的前置排除，以及对每场独立验收的回归。完整 JSON、原文和模型回包只在本机私有临时样本中核对，没有提交业务内容、密钥或编译产物。

## 验证和启用

源码先提交到 feature 分支，每次提交合入本地 develop 后再验证。明确的短剧 PHPUnit 文件清单覆盖原上下文、时长、对白、场景绑定、剧情记忆、输入契约、请求签名、整集/连续性复核，以及新增合并、混合成功失败、截断、拒绝、未知异常、事务回滚、租户隔离、单次调度中断恢复、旧单元保护和策略启用隔离。最终 261 tests、5850 assertions 全部通过，PHP 语法和差异空白检查通过。真实模型仅执行上述两次已获授权的对照。

真实对照通过后，将服务端新任务默认策略启用。必须让常驻短剧 worker 加载本次源码；关闭策略的在途任务保持原路径，旧版本任务不升级输入协议。最终测试数量、源提交和本地 worker 状态见本次交付记录。
